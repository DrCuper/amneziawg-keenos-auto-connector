# Design

## Context

`syncer.Syncer.Run` возвращает `*Result` (группы с версиями и `+N/-M`,
`router.ApplyResult` с планом, числом команд, бэкапом) и ошибку, из которой
видно, что именно сломалось: `router.TransportError` (роутер недоступен после
ретраев), `router.CommandError`/`VerifyError` (роутер ответил, но изменение не
прошло), `ErrGroupsFailed` (часть групп не собралась), `router.ErrLocked`
(занято другим запуском). Этого достаточно и для журнала, и для алертов — нужно
только доставить результат наружу, не меняя логику синхронизации.

Запуски бывают из двух мест: демон `serve` (cron, старт) и ручной CLI, причём
одновременно — это разные процессы с общим `state_dir`.

## Goals / Non-Goals

**Goals:**
- Журнал, который отвечает на «что, когда, куда и чем закончилось» без
  внешней БД и переживает перезапуски; dry‑run виден отдельно от реальных применений.
- Алерты, которые не спамят: одно сообщение на инцидент, редкие напоминания,
  сообщение о восстановлении — в том числе когда инцидент начался в демоне, а
  закончился ручным `awgkeen sync`.
- Секреты каналов вне репозитория и вне логов.
- Точка расширения для этапа 4 (AWG) и этапа 5 (REST API читает журнал и алерты).

**Non-Goals:**
- Метрики Prometheus, веб‑интерфейс, REST API.
- Встроенная проверка AWG по handshake — этап 4; сейчас — внешний хук.
- Доставка «ровно один раз»: при сбое канала сообщение повторится при
  следующем событии, а не будет потеряно.

## Decisions

1. **Наблюдатели вместо зависимостей.** `syncer` объявляет
   `Observer { Observe(ctx, *Report) }` и `Report{Kind, Trigger, DryRun,
   Started, Duration, Result, Err, Manual}`; `Run`, `Rollback` и ручные правки
   вызывают наблюдателей после завершения. `journal` и `notify` импортируют
   `syncer`, а не наоборот — циклов нет, `syncer` тестируется без них.
   Наблюдатель не может провалить синхронизацию: ошибки записи журнала и
   отправки только логируются.

2. **Журнал — JSON Lines** в `state_dir/journal.jsonl`: одна строка — одна
   запись, добавление в конец, читается `grep`/`jq`, без схемы и миграций.
   Запись под файловой блокировкой (`internal/lock`, `journal.lock`), номер
   записи — монотонный счётчик в `journal.seq` (при потере — максимум из
   журнала). Повреждённая строка пропускается при чтении с предупреждением.
   Альтернатива SQLite отложена: для сотен записей в сутки файл проще, а
   интерфейс чтения (`Query`) позволит заменить хранилище на этапе 5.

3. **Что пишется.** Вид (`sync`, `rollback`, `manual`, `router-apply`),
   источник (`cli`, `schedule`, `startup`), `dry_run`, статус (`ok`, `partial`,
   `failed`, `skipped`), `changed`, ошибка, длительность, группы (версия,
   предыдущая применённая, записей, `+N/-M`, новая/закреплена, ошибка), число
   команд, `saved`, путь бэкапа и строки диффа плана (не больше
   `journal.max_changes`, остаток — счётчиком). Полное содержимое версий в
   журнал не копируется — оно уже в `groups/<name>/v<N>.json`.

4. **Ротация.** Записи старше `journal.keep_days` и сверх
   `journal.max_entries` удаляются атомарной перезаписью файла: раз в сутки в
   `serve`, по `journal prune` и автоматически, когда файл превысил 16 МиБ.

5. **Модель алерта.** Ключ (`router_unreachable`, `sync_failed`,
   `awg_down:<check>`) → `{active, since, failures, last_sent, notified,
   detail}`. Сигнал «плохо» увеличивает `failures`; при `failures ≥
   fail_threshold` алерт становится активным и отправляется `firing`; пока
   активен — молчание, кроме `reminder` раз в `repeat_interval` (0 — никогда);
   сигнал «хорошо» у активного алерта отправляет `resolved` с длительностью и
   сбрасывает состояние. Если отправка `firing` не удалась ни в один канал,
   `notified=false` и попытка повторяется при следующем сигнале. Состояние —
   `state_dir/alerts.json` под блокировкой `alerts.lock`, общее для демона и CLI.

6. **Классификация результата синхронизации** (только реальные запуски
   `sync`/`rollback`; dry‑run и ручные правки алертов не меняют):

   | Результат | `router_unreachable` | `sync_failed` |
   |---|---|---|
   | успех | хорошо | хорошо |
   | `TransportError` | плохо | без изменений |
   | `ErrLocked`, отмена контекста | без изменений | без изменений |
   | прочая ошибка, роутер ответил (`Result.Apply != nil`) | хорошо | плохо |
   | прочая ошибка, до роутера не дошли | без изменений | плохо |

   Так недоступный роутер даёт один алерт, а не два.

7. **Проверки здоровья.** `health.Check{Name, Alert, Run(ctx) error}`:
   встроенная проверка роутера (`ReadState`, алерт `router_unreachable`) и
   хуки `health.checks` — внешняя команда (argv без shell, таймаут), код 0 —
   «хорошо», иначе «плохо» с хвостом вывода; алерт по умолчанию `awg_down`.
   `serve` запускает их каждые `health.interval` (0 — выключено). Этап 4
   добавит встроенную проверку AWG тем же интерфейсом.

8. **Каналы.** `Channel{Name, Send(ctx, Message)}`; `Message{Event, Alert, Key,
   Title, Text, Since, Failures, Time, Host}`.
   * Telegram: `POST {api_url}/bot<token>/sendMessage`, простой текст без
     разметки (не нужно экранирование), обрезка до 4096 символов, 429 и 5xx
     повторяются с учётом `retry_after`.
   * Webhook: `POST` JSON `Message`, заголовки `X-Awgkeen-Event` и, при
     заданном секрете, `X-Awgkeen-Signature: sha256=<hmac>`; 5xx и сетевые
     ошибки повторяются, 4xx — нет.
   Ошибки каналов очищаются от токена и полного URL (в логах остаётся только
   хост), потому что `net/http` включает URL в текст ошибки.

9. **Секреты.** `notify.telegram.bot_token`, `chat_id`, `webhooks[].url`,
   `secret` могут лежать в YAML, но рекомендуются переменные окружения
   (`AWGKEEN_TELEGRAM_BOT_TOKEN`, `AWGKEEN_TELEGRAM_CHAT_ID`,
   `AWGKEEN_WEBHOOK_URL`, `AWGKEEN_WEBHOOK_SECRET` — для первого webhook) или
   файлы (`bot_token_file`, `secret_file`) — например, Docker secrets.
   Окружение важнее файла, файл важнее YAML.

## Risks / Trade-offs

- [Синхронная отправка задерживает CLI] → таймаут канала 10 с и 2 повтора по
  умолчанию; отправка идёт после вывода результата не раньше, чем закончилась
  синхронизация, а ошибки каналов не меняют код возврата.
- [Два процесса пишут журнал] → flock на запись; чтение без блокировки
  терпит недописанную последнюю строку.
- [Хук проверки — произвольная команда] → запускается без shell, только из
  конфига оператора, с таймаутом; вывод в сообщении обрезается.
- [Флаппинг] → `fail_threshold` (по умолчанию 1) позволяет требовать N неудач
  подряд до алерта.
