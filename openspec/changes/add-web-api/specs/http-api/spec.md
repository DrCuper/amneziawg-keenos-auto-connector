# Spec Delta

## Purpose

REST API демона `awgkeen serve`: просмотр и изменение групп, синхронизация,
журнал, алерты, проверки, состояние роутера, AWG‑туннели и метрики.

## ADDED Requirements

### Requirement: Запуск API
`awgkeen serve` SHALL поднимать HTTP‑сервер на `api.listen`, если он задан, и
останавливать его штатно при завершении. При `tls_cert_file`/`tls_key_file`
SHALL использоваться HTTPS. Пустой `api.listen` SHALL отключать API.

#### Scenario: API выключен
- **WHEN** `api.listen` пуст
- **THEN** `serve` не открывает HTTP‑порт

#### Scenario: Порт занят
- **WHEN** `api.listen` занят другим процессом
- **THEN** `serve` завершается с ошибкой до запуска планировщика

### Requirement: Авторизация
Все эндпоинты, кроме `GET /api/v1/health`, SHALL требовать заголовок
`Authorization: Bearer <token>`: `api.token` даёт полный доступ,
`api.read_token` — только GET. Токены SHALL читаться из
`AWGKEEN_API_TOKEN`/`AWGKEEN_API_READ_TOKEN`, `*_file` или YAML. Без токенов
API SHALL быть разрешено только на loopback; иначе конфиг MUST отклоняться.

#### Scenario: Нет токена
- **WHEN** запрос `GET /api/v1/groups` без заголовка при заданном `api.token`
- **THEN** ответ 401

#### Scenario: Токен только на чтение
- **WHEN** `POST /api/v1/sync` с `read_token`
- **THEN** ответ 403, синхронизация не запускается

#### Scenario: Внешний адрес без токена
- **WHEN** `api.listen: 0.0.0.0:8080` и токен не задан
- **THEN** конфиг не загружается с ошибкой про `api.token`

### Requirement: Группы и правки
API SHALL отдавать список групп (подключение, источники, последняя,
применённая и закреплённая версии, ручные записи), группу с записями
выбранной версии и историю версий. API SHALL принимать ручные добавления,
удаления, сброс, открепление и откат к версии, с немедленной синхронизацией
группы по флагу `apply`. Неизвестная группа — 404, неверные записи — 400.

#### Scenario: Добавить домен и применить
- **WHEN** `POST /api/v1/groups/a/manual {"add":["x.example"],"apply":true}`
- **THEN** создана новая версия группы с `x.example`, она применена на роутер, ответ содержит дифф

#### Scenario: Откат
- **WHEN** `POST /api/v1/groups/a/rollback {"to":1}`
- **THEN** группа закреплена на версии 1 и применена

### Requirement: Синхронизация через API
`POST /api/v1/sync` SHALL запускать синхронизацию всех или выбранных групп с
`dry_run` и `force`. Ответ SHALL содержать запись журнала операции, сводку и
план; ошибка операции — 422 (409 при блокировке роутера) с тем же телом.

#### Scenario: Dry-run
- **WHEN** `POST /api/v1/sync {"dry_run":true}`
- **THEN** ответ содержит план, роутер и состояние не изменены

### Requirement: Одна операция за раз
Изменяющие операции API, запуски по cron и импорт туннелей при старте SHALL
выполняться последовательно. Если операция уже идёт, изменяющий запрос API
SHALL получать 409; запросы на чтение MUST NOT ждать.

#### Scenario: Занято
- **WHEN** идёт синхронизация по расписанию, приходит `POST /api/v1/sync`
- **THEN** ответ 409, а `GET /api/v1/groups` отвечает сразу

### Requirement: Журнал, алерты, проверки, роутер
API SHALL отдавать журнал с фильтрами `group`, `kind`, `status`, `since`,
`dry_run`, `limit` и запись по номеру; активные и прошлые алерты; последние
результаты проверок; сводку `/api/v1/status`; состояние роутера (группы,
маршруты, Wireguard‑интерфейсы). Ключи AWG MUST NOT возвращаться ни одним
эндпоинтом. Операции из API SHALL записываться в журнал с источником `api`.

#### Scenario: Журнал по группе
- **WHEN** `GET /api/v1/journal?group=a&since=7d`
- **THEN** возвращены операции с группой `a` за 7 дней, новые первыми

#### Scenario: Без ключей
- **WHEN** запрошены `/api/v1/router` и план `/api/v1/tunnels/apply`
- **THEN** приватные и preshared‑ключи в ответах отсутствуют, в плане `<secret>`

### Requirement: Туннели через API
API SHALL отдавать список туннелей с интерфейсами, их состояние (handshake,
endpoint, трафик, здоров ли) и выполнять план/импорт туннелей с записью в
журнал.

#### Scenario: Импорт
- **WHEN** `POST /api/v1/tunnels/apply {}`
- **THEN** туннели импортированы, ответ содержит интерфейсы и запись журнала `awg-apply`

### Requirement: Метрики
`GET /metrics` SHALL отдавать текстовый формат Prometheus: работа сервиса,
результат каждой проверки, активность алертов, размер и применённая версия
групп, время и успех последней синхронизации.

#### Scenario: Скрейп
- **WHEN** Prometheus запрашивает `/metrics` с токеном
- **THEN** ответ содержит `awgkeen_up 1` и `awgkeen_check_ok{check="..."}`
