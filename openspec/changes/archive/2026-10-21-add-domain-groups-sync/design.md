# Design

## Context

Этап 1 дал `router.Client` с `Apply(ctx, *Desired, dryRun)`: он сам берёт
блокировку, читает running‑config, делает бэкап, строит дифф, применяет,
проверяет и сохраняет. Этап 2 должен **производить `Desired`** из источников и
управлять историей — и не трогать клиент.

Факты о Keenetic, важные для этапа:

* `object-group fqdn … include example.com` покрывает домен и все его
  поддомены — поэтому поддомены в группе избыточны и их можно схлопывать.
* Документированного лимита записей нет; по опыту сообщества группы в
  несколько тысяч записей замедляют dns‑proxy и загрузку конфигурации. Лимит
  оставляем настраиваемым (`router.max_entries`, по умолчанию 2000) и
  даём выбор `error|truncate`.
* Community‑списки идут в разных форматах (plain, hosts, dnsmasq‑директивы,
  v2fly `domain:`, Clash `DOMAIN-SUFFIX`). Один парсер с автоопределением
  построчно покрывает их все.

## Goals / Non-Goals

**Goals:**
- Чистая сборка группы: `(spec, sources, manual) → Entries` без I/O в тестах.
- Файловое состояние с версиями, пригодное для позднейшего REST API; интерфейс
  `store.Store`, чтобы SQLite можно было подставить без изменения `syncer`.
- Безопасность по умолчанию: dry‑run ничего не пишет, упавший источник не
  опустошает группу, резкое сокращение требует `--force`.
- Планировщик без внешних сервисов: демон `serve` + cron‑выражение.

**Non-Goals:**
- Журнал изменений и уведомления (этап 3): `syncer.Result` уже содержит всё
  нужное, но никуда не отправляется.
- HTTP API (этап 5).
- Выдача IP‑адресов из резолва доменов (используем только fqdn‑группы).

## Decisions

1. **Подключения как отдельная сущность.** Группа ссылается на `connection`
   по имени, а маршруты (`dns-proxy route`) описаны один раз на подключение.
   Так одно изменение интерфейса (например, `Wireguard0` → `Wireguard1`)
   переводит все группы подключения. Альтернатива — `routes` прямо в группе
   (как в `examples/groups.yaml` этапа 1) — остаётся доступной через
   `router plan|apply`, но `sync` работает только через подключения.

2. **Пакеты.**
   ```
   internal/source    Fetcher (HTTP с кэшем/условным GET, файлы), Parse(format, text)
   internal/domains   Spec (YAML), Normalize, Build(group) → Entries + Stats
   internal/store     Store: группы (версии, applied, pinned, manual), кэш источников; файловая реализация
   internal/syncer    Syncer: Build всех групп → Desired → Client.Apply; Rollback; Scheduler (cron)
   ```
   `domains` не знает про store и роутер; `syncer` — единственный оркестратор.

3. **Версии = снимки содержимого.** Версия содержит полный список записей
   (не дифф), хэш `sha256` отсортированного содержимого, статистику источников.
   Полный снимок делает откат тривиальным и независимым от истории. Хранится
   `keep_versions` последних (по умолчанию 10); закреплённая и применённая
   версии не удаляются.

4. **Файловое состояние.**
   ```
   state_dir/
     groups/<name>/state.json        applied, pinned, manual include/remove
     groups/<name>/v<N>.json          версия N
     cache/<sha256(url)>.json         тело, etag, last-modified, fetched_at
   ```
   Запись через временный файл + `rename`. Один каталог на группу: ошибка в
   одной группе не трогает остальные; версии — отдельные файлы, чтобы большие
   списки не переписывались целиком при каждой правке `state.json`.

5. **Приоритет записей при обрезке:** ручные `include` (YAML, затем CLI) →
   источники в порядке объявления. Это детерминировано и объяснимо
   оператору; «важные» домены он ставит в `include`.

6. **Схлопывание поддоменов** делается после объединения всех источников и
   до проверки лимита — так лимит считается по тому, что реально уйдёт на
   роутер. `exclude` (Keenetic) не участвует в схлопывании: он нужен именно
   для поддомена более широкой записи.

7. **Защита от опустошения считается относительно применённой версии**, а не
   последней собранной: если источник «моргнул» два раза подряд, вторая
   сборка не должна проходить только потому, что первая уже маленькая.
   При отсутствии применённой версии (первый запуск) защита не действует.

8. **Dry‑run на уровне syncer**, а не только клиента: `--dry-run` собирает
   группы в памяти, печатает сводку и план, но не пишет версии и
   applied/pinned. Кэш источников обновлять можно — это не состояние групп.

9. **Планировщик — `robfig/cron/v3`** со стандартными 5 полями и дескрипторами
   (`@hourly`, `@every 6h`); таймзона процесса. Пропуск пересекающихся запусков
   через `cron.SkipIfStillRunning`. Ручной `sync` параллельно с демоном
   исключается файловой блокировкой клиента (`router.lock_file`), поэтому в
   демоне `lock_file` обязателен (предупреждение, если пуст).

10. **Dедупликация ошибок сборки vs применения.** Сборка выполняется для всех
    групп; группы с ошибкой исключаются из `Desired` (их состояние на роутере
    не трогается, т.к. `Prune` берётся из spec‑файла и применяется только к
    группам, которых нет в файле вообще). Применение — один вызов `Apply` на
    все собранные группы: один бэкап, одна блокировка, одно сохранение.

## Risks / Trade-offs

- **Полные снимки версий** занимают место: 10 версий × 2000 записей ≈ 0.5 МБ
  на группу — приемлемо.
- **Автоопределение формата** может принять за домен строку мусора; поэтому
  после разбора каждая запись проходит `router.ValidateEntry`, а TLD без точки
  и служебные имена отбрасываются.
- **`Prune`** из spec‑файла удаляет на роутере группы, которых нет в файле;
  при ошибке сборки группа всё равно есть в файле → не удаляется.
- Клиент применяет все группы одним планом; ошибка на команде одной группы
  прерывает план (поведение этапа 1). Это сознательно: лучше остановиться и
  показать, чем продолжать с частично применённым состоянием.

## Migration Plan

Новые команды и секции конфига; `router plan|apply` с `groups.yaml` продолжают
работать. Для перехода оператор переносит `routes` из групп в `connections`
и добавляет `sources`.

## Open Questions

- Нужна ли поддержка `.lst`‑списков с IP/CIDR в отдельные группы для
  `ip`‑object‑group? Пока CIDR принимаются внутрь fqdn‑группы (как на этапе 1).
- SQLite вместо файлов — только если появится REST API с запросами по истории.
