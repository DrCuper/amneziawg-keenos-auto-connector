# Spec Delta

## Purpose

Клиент роутера даёт сервису единый безопасный способ читать конфигурацию Keenetic
и менять доменные группы (`object-group fqdn`) и DNS‑маршруты (`dns-proxy route`)
с предварительным планом, dry‑run, бэкапом и защитой от параллельных изменений.

## ADDED Requirements

### Requirement: Транспорт выбирается конфигурацией
Клиент SHALL поддерживать два транспорта — RCI (HTTP‑API KeeneticOS) и SSH —
выбираемые в конфигурации; оба исполняют команды CLI KeeneticOS и возвращают
текст `running-config`.

#### Scenario: RCI‑транспорт
- **WHEN** в конфиге `router.transport: rci` и заданы `url`, `username`, пароль
- **THEN** клиент авторизуется по challenge‑response схеме Keenetic и выполняет команды через `POST /rci/`

#### Scenario: SSH‑транспорт
- **WHEN** в конфиге `router.transport: ssh` и заданы `host`, `username` и пароль или ключ
- **THEN** клиент выполняет команды CLI через SSH‑сессию

#### Scenario: Неизвестный транспорт
- **WHEN** в конфиге указан неподдерживаемый транспорт
- **THEN** клиент возвращает ошибку конфигурации до любого обращения к роутеру

### Requirement: Учётные данные берутся из конфига или окружения
Пароль и путь к ключу SHALL приниматься из YAML‑конфига либо из переменных
окружения `AWGKEEN_ROUTER_PASSWORD` и `AWGKEEN_ROUTER_KEY_FILE`; значение из
окружения MUST иметь приоритет над конфигом. Секреты MUST NOT попадать в логи и
вывод плана.

#### Scenario: Пароль из окружения
- **WHEN** в YAML пароль пустой, а `AWGKEEN_ROUTER_PASSWORD` задана
- **THEN** клиент использует значение из окружения

#### Scenario: Пароль нигде не задан
- **WHEN** ни конфиг, ни окружение не содержат пароля/ключа
- **THEN** создание клиента завершается ошибкой с понятным сообщением

### Requirement: Чтение текущего состояния
Клиент SHALL читать `running-config` и возвращать структурированное состояние:
список групп `object-group fqdn` (имя, description, include, exclude) и список
правил `dns-proxy route object-group` (группа, интерфейс/шлюз, auto, reject) с
сохранением порядка.

#### Scenario: Группа с include и exclude
- **WHEN** running-config содержит `object-group fqdn test` с `include a.com`, `include b.com`, `exclude x.a.com`
- **THEN** состояние содержит группу `test` с include `[a.com, b.com]` и exclude `[x.a.com]`

#### Scenario: Маршрут с флагами
- **WHEN** running-config содержит `route object-group test Wireguard2 auto reject` внутри секции `dns-proxy`
- **THEN** состояние содержит маршрут {group: test, interface: Wireguard2, auto: true, reject: true}

#### Scenario: Пустая конфигурация
- **WHEN** running-config не содержит групп и маршрутов
- **THEN** состояние содержит пустые списки без ошибки

### Requirement: План изменений (дифф)
Клиент SHALL строить план как разницу между текущим и желаемым состоянием:
только команды, меняющие состояние, в порядке «создать группу → include/exclude →
маршруты → удаление лишнего». При совпадении состояний план MUST быть пустым.

#### Scenario: Новая группа
- **WHEN** желаемая группа отсутствует на роутере
- **THEN** план содержит `object-group fqdn <name>`, по одной команде на каждый include/exclude и description

#### Scenario: Частичное обновление
- **WHEN** на роутере группа содержит `a.com, b.com`, а желаемая — `b.com, c.com`
- **THEN** план содержит только `include c.com` и `no include a.com`

#### Scenario: Без изменений
- **WHEN** текущее и желаемое состояние совпадают
- **THEN** план пуст и применение не выполняет ни одной команды и не сохраняет конфиг

#### Scenario: Привязка маршрута
- **WHEN** желаемая группа требует маршрут на интерфейс, а на роутере его нет
- **THEN** план содержит `dns-proxy route object-group <name> <iface> auto`

### Requirement: Dry-run
Клиент SHALL поддерживать режим dry‑run, в котором план строится и выводится в
человекочитаемом виде, но ни одна изменяющая команда MUST NOT отправляться на роутер.

#### Scenario: Dry-run с изменениями
- **WHEN** вызвано применение с `dry_run=true` и план не пуст
- **THEN** возвращается план с командами и диффом, а транспорт получил только команды чтения

### Requirement: Применение с проверкой и сохранением
При применении клиент SHALL выполнить команды плана, перечитать состояние,
убедиться, что желаемое достигнуто, и затем выполнить `system configuration save`
(если сохранение не отключено). Команда, завершившаяся ошибкой роутера, MUST
прервать применение с ошибкой, содержащей команду и ответ роутера.

#### Scenario: Успешное применение
- **WHEN** все команды плана выполнены без ошибок и перечитанное состояние совпадает с желаемым
- **THEN** выполняется сохранение и возвращается результат с числом применённых команд

#### Scenario: Ошибка роутера
- **WHEN** роутер отвечает ошибкой на одну из команд
- **THEN** применение прекращается, сохранение не выполняется, ошибка содержит команду и текст ответа

#### Scenario: Расхождение после применения
- **WHEN** после применения перечитанное состояние не содержит ожидаемой записи
- **THEN** возвращается ошибка верификации, сохранение не выполняется

### Requirement: Бэкап перед изменениями
Перед выполнением непустого плана клиент SHALL сохранить текущий `running-config`
в файл в каталоге бэкапов с меткой времени, если каталог задан в конфигурации.

#### Scenario: Бэкап создан
- **WHEN** задан `router.backup_dir` и план не пуст
- **THEN** до первой изменяющей команды в каталоге появляется файл с running-config

### Requirement: Таймауты и ретраи
Каждая операция транспорта SHALL ограничиваться таймаутом из конфигурации.
Транспортные ошибки (сеть, таймаут, 5xx) SHALL повторяться до `retries` раз с
экспоненциальной задержкой; ошибки роутера на команду MUST NOT повторяться.

#### Scenario: Временная ошибка сети
- **WHEN** первое обращение к роутеру завершается сетевой ошибкой, а второе — успешно
- **THEN** операция завершается успешно, число попыток = 2

#### Scenario: Исчерпание ретраев
- **WHEN** все попытки завершились транспортной ошибкой
- **THEN** возвращается ошибка с числом попыток и последней причиной

#### Scenario: Ошибка команды не ретраится
- **WHEN** роутер вернул ошибку на команду
- **THEN** повторной отправки той же команды не происходит

### Requirement: Блокировка от параллельных изменений
Клиент SHALL брать блокировку (внутрипроцессную и файловую, если задан
`lock_file`) на время применения; вторая попытка применения в это время MUST
завершаться ошибкой «занято» без ожидания дольше настроенного.

#### Scenario: Параллельное применение
- **WHEN** одно применение выполняется, а второе стартует
- **THEN** второе получает ошибку блокировки и не отправляет команд

### Requirement: CLI-команды для оператора
Бинарник SHALL предоставлять команды `router show`, `router plan`,
`router apply [--dry-run]` и `router save`, читающие конфиг из `--config`.

#### Scenario: Plan из файла желаемого состояния
- **WHEN** оператор запускает `router plan --desired groups.yaml`
- **THEN** выводится список команд и дифф, код возврата 0, роутер не изменён
